# 可行性分析报告

> 项目：目标适应症及用药数据分析系统  
> 编制：杨博文  
> 日期：2026-11-12

## 1 项目背景

医药流通过程中会产生大量处方数据，涵盖医院、科室、医生职称、患者年龄与性别、药品、诊断等多类信息。这些数据分散在不同系统中，缺少统一的多维分析视图，药品与适应症之间的对应关系也不够透明。本项目以 100 万条脱敏处方记录为基础，构建“目标适应症及用药数据分析系统”，提供 12 个 BI 分析接口和 1 个可视化大屏，面向医药企业市场部门、医院药事管理部门和药品流通企业，支持按城市等级、年龄、省份、疾病、药品、科室等维度查看用药趋势。

## 2 技术可行性

项目采用“存储—计算—预计算—应用”四层架构，各层均使用成熟的开源组件，技术路线清晰，具备落地条件。

| 层次 | 技术方案 | 关键指标 |
|---|---|---|
| 存储层 | HDFS 分布式存储 + MySQL 关系库 | 3 个节点，原始数据约 240MB |
| 计算层 | Hive 外部表 + MapReduce 分布式计算 | 100 万行全表聚合实测 17.67 秒 |
| 预计算层 | Kylin 多维预计算，结果存入 HBase | 8 个维度、4 个度量 |
| 应用层 | SpringBoot 提供接口，Vue + ECharts 渲染 | 12 个接口、1 个可视化大屏 |

核心链路的实测数据如下：

```text
全表 count(1)：100 万行，MapReduce 作业，耗时 17.67 秒
HDFS 存储：文件副本 2 份，分布在 2 个 DataNode 节点
MySQL 明细查询：已建 hosp_id 索引，聚合查询毫秒级
```

项目执行中也遇到并解决了实际技术风险。HBase 1.2.1 自带的 Hadoop 客户端版本为 2.5.1，而集群 Hadoop 版本为 2.7.3，两者在作业提交与文件本地化环节不兼容，导致 `hbase Import` 多次提交失败，先后出现 `Resource ... changed on src filesystem`、`job.split does not exist`、`Input path does not exist` 等错误。经评估，将数据链路由“txt → SequenceFile → HBase → Hive 外部表”调整为“txt → HDFS → Hive 外部表”，查询结果与调整前一致，100 万行 `count(1)` 经 MapReduce 实测返回 1000000。调整后 HBase 由业务明细存储改为承担 Kylin 元数据与 Cube 实体的存储职责，表名与字段名未变，对 T5、T6、T7、T8 无影响。该方案降低了组件耦合度，技术风险可控。

综上，项目在存储、计算、预计算和应用四个层面均有成熟方案支撑，核心技术链路已通过 100 万条真实数据验证，技术上可行。

## 3 经济可行性

项目投入以现有实训环境和开源软件为主，不产生额外采购费用。

| 投入项 | 说明 |
|---|---|
| 硬件 | 3 台虚拟机，使用现有实验环境，无额外采购 |
| 软件 | Hadoop、Hive、HBase、Kylin、SpringBoot、Vue 等全部开源，零授权费用 |
| 人力 | 项目组 5 人，工期 5 天 |
| 运维 | 单机化部署，无云服务租金与外包费用 |

项目产出主要体现在三个方面：一是替代人工汇总处方报表，减少重复统计工作；二是把按天出报表缩短到秒级查询，提高分析效率；三是数据模型与接口可复用到其他药品品类，具备扩展价值。整体投入以开源软件和现有实验环境为主，无软件采购支出，经济上可行。

## 4 操作可行性

系统以浏览器图形界面为主，不同角色均可快速上手。

| 角色 | 主要操作 | 培训需求 |
|---|---|---|
| 医药企业市场人员 | 在网页查看 12 个分析图表和可视化大屏 | 不需要，界面即用 |
| 数据分析人员 | 通过接口取数，进行二次分析 | 需要阅读接口文档 |
| 运维人员 | 启停集群、备份配置、处理常见异常 | 需要一份操作手册 |

用户通过浏览器访问，不需要安装客户端；图表采用柱状图、折线图、饼图、地图等常见形式，不需要学习新的交互概念。日常运维按固定的组件启停顺序执行，异常时先检查进程，再检查配置与日志，操作复杂度可控。因此，系统在操作上可行。

## 5 结论

综上所述，本系统在技术上有成熟开源组件支撑，核心链路已通过 100 万条真实数据的实测验证；在经济上无软件采购成本，投入集中在现有环境内；在操作上以浏览器图形界面为主，用户无需额外培训。项目具备可行性，建议按计划实施。
