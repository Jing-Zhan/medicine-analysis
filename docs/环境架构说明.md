## 一、这个项目最终要交什么

一句话：**把 6 个 txt 数据文件，变成网页上的 12 张图 + 1 个数据大屏。**

具体四个交付物：

| 交付物 | 技术 | 端口 | 谁做 |
|---|---|---|---|
| 12 个数据接口 | SpringBoot + MyBatis | 83 | 后端 |
| 12 个图表页面 | Vue2 + ECharts，打包后放 Tomcat | 8080 | 前端 |
| 1 个可视化大屏 | Python + Django + ECharts | 8000 | 大屏 |
| 底层数据平台 | 3 节点 Hadoop + Hive + Kylin | — | 环境 |

**关键理解**：前面三个是"看得见的东西"，最后一个是"让前三样有数据可用的地基"。地基不稳，上面三样全是空壳。

## 二、一条数据的一生 ⭐（这是整套协同逻辑的核心）

不讲抽象概念，就跟**一条真实的处方记录**走完全程。

这条记录来自 `yiyao.txt` 的第一行：

```
200812009000000  1100064  200812  3.9650633  19.825317  10  48  DM0000178036_2
（记录号）（文件号）（年月）（数量）（金额）（...）...
```

### 站点 ① 原料：txt 文件躺在硬盘上

```
/opt/bi_data/mysql_data/yiyao.txt        181 MB，100 万行
/opt/bi_data/mysql_data/t_view_drug.txt   52 MB
... 一共 6 个文件，合计约 240 MB
```

- **谁放进去的**：环境镜像自带，老师提供的原始数据
- **它是什么**：纯文本，一行一条记录，字段用 Tab 分隔，`\N` 表示空值
- **没有它会怎样**：后面全都没数据，项目是个空壳

> 这一站**不需要人管**，它一直在。

---

### 站点 ② 明细仓库：MySQL（给大屏用）

```
MySQL 5.7.28  →  库 yiyao  →  6 张表
                prescription_diseases  100 万行
                disease 42501 / drug 232574 / hospital 1728
                hosp_area 1777 / section 319
```

- **谁做的**：占竞（已全部导入完成）
- **它的角色**：**存全量明细**，一行一行原样存着，要什么查什么
- **谁在用它**：**Django 大屏直接连 MySQL 取数**（不经过 Kylin）
- **为什么大屏不绕 Kylin**：大屏的图比较"重"，需要明细级别的过滤和拼装，MySQL 的索引够用，链路短、调试快
- **没有它会怎样**：大屏没数据

**比喻**：MySQL 就像**仓库的原始账本**，每一笔都在，随便翻。

---

### 站点 ③ 分布式硬盘：HDFS（让三台机器合体）

```
HDFS  hdfs://master:9000/bi_data/mysql/
      ├── t_view_areas/t_view_areas.txt          153 KB
      ├── t_view_disease/t_view_disease.txt      5.1 MB
      ├── t_view_drug/t_view_drug.txt             52 MB
      ├── t_view_hosp/t_view_hosp.txt            125 KB
      ├── t_view_section/t_view_section.txt       12 KB
      └── yiyao/yiyao.txt                        181 MB
```

- **谁做的**：占竞（11/11 18:21 上传完成）
- **它解决什么**：单台机器的硬盘不够大、也不够快；HDFS 把 master + slave1 + slave2 的硬盘**拼成一块**，一个文件会被切成块、存 3 份（副本数=3）散在三台上
- **为什么必须走这一步**：MapReduce 的计算任务会**分发到 slave1、slave2 上去跑**，slave 只能读自己那台能访问的存储。文件如果只躺在 master 的本地硬盘，slave 读不到，作业必失败
- **没有它会怎样**：所有计算只能在 master 一台机器上跑，等于没有集群

**比喻**：HDFS 就像**把三个人的书柜联网成一个图书馆**，谁都能来借，不用管书在谁的柜子里。

> ⚠️ **这一站踩过的最大的坑**：数据一开始是直接放在 master 本地硬盘的，Hive 表指向 `file:/bi_data/...`。因为只有 master 能看见，slave 上的计算任务全报 `File ... does not exist`。11/11 18:21 才把数据搬进 HDFS 并改了表指向，这个问题解决。

---

### 站点 ④ 表结构：Hive（给文件套一层"表"）

```
Hive 库 bigdata，6 张外部表，实际数据都在 HDFS 上：

  bigdata.disease               → hdfs://.../t_view_disease
  bigdata.drug                  → hdfs://.../t_view_drug
  bigdata.hosp_area             → hdfs://.../t_view_areas     ← 注意名字
  bigdata.hospital              → hdfs://.../t_view_hosp      ← 注意名字
  bigdata.prescription_diseases → hdfs://.../yiyao
  bigdata.section               → hdfs://.../t_view_section
```

### 🔑 这里是最容易误解的一点，请务必看懂

**Hive 不存数据，它只存"这张表叫什么、有哪些列、文件在哪"。**

打个比方：
- HDFS 里的 `yiyao.txt` 就是**一个 Excel 文件**
- Hive 表 `prescription_diseases` 就是**"用哪套列名去读这个文件"的说明书**
- 建 Hive 表的时候 **一行数据都没复制**，只是登记了一下路径和列定义

证据：`ALTER TABLE ... SET LOCATION 'hdfs://...'` 这条命令**几毫秒就执行完了**（截图里 `Time taken: 0.035 seconds`）。如果是搬 181MB 数据，不可能这么快。

- **谁做的**：占竞（建表 + 改指向）
- **它解决什么**：HDFS 里的文件是没结构的纯文本，不会写 Java 的人用不了。Hive 让它变成能 `SELECT ... GROUP BY` 的表
- **谁在用它**：**Kylin 通过 Hive 的元数据来找数据**
- **没有它会怎样**：Kylin 不知道数据长什么样，建不了模型

**比喻**：Hive 就像**图书馆的检索卡片柜**，书还在书架上（HDFS），卡片上写着"这本书在几号架"。

> ⚠️ **踩过的坑**：6 张表的名字不都跟目录名一样。`t_view_areas` 对应的表叫 `hosp_area`（不是 `areas`），`t_view_hosp` 对应的表叫 `hospital`（不是 `hosp`）。写错表名会报 `Table not found`。

### 站点 ⑤ 提前算好的答案册：Kylin Cube

```
Kylin 3.1.1  →  项目 yiyao  →  数据源 bigdata（Hive）  →  模型 bi_model  →  Cube bi_cube
```

- **谁做的**：占竞（**进行中**，还没开始建）
- **它解决什么**：Hive 每次查都要扫全表，100 万行聚合一次要几十秒，12 张图逐个查就是几分钟。Kylin 的做法是**提前把所有维度组合的结果算好，存起来**，查询时直接取答案，毫秒级返回
- **它怎么工作**：读 Hive 表 → 跑一个 MapReduce 作业 → 把结果写进 HBase 的 Cube 表
- **谁在用它**：SpringBoot 通过 JDBC 连它
- **没有它会怎样**：接口能跑，但每张图都要等几十秒，演示效果很差

**比喻**：Kylin 就像**考试前把所有可能考到的题都算好答案，做成一本答案册**。考试时不用现场算，直接翻书。

**代价**：做这本答案册很慢（建 Cube 十几分钟起），而且维度配错了要整本重做。**这是整个项目最耗时的环节。**

## 三、四个"协同关系"（把抽象的东西说透）

上面是按数据流讲的，这里是按"谁依赖谁"讲的。**答辩时被追问，答的就是这四条。**

### 关系 1：ZooKeeper 和所有人 —— "微信群"

- ZooKeeper 是个**通讯录 + 群公告**，本身不存业务数据
- HBase 启动时第一件事是去 ZooKeeper 登记"我在 slave1 上，我活着"
- Kylin 也去 ZooKeeper 登记自己的集群名
- **ZK 挂了会怎样**：HBase 直接起不来（找不到自己该在哪），Kylin 也起不来

### 关系 2：HDFS 和计算 —— "共享硬盘"

- 计算任务（MapReduce）是**分发到 slave1、slave2 上跑**的
- 任务代码在 slave 上执行，它要读的数据**必须在 HDFS 上**
- **数据在本地硬盘会怎样**：slave 读不到 → `File ... does not exist` → 作业失败

这就是上面提到的那个大坑，本质是"共享硬盘没共享"。

### 关系 3：Hive 和 HDFS —— "卡片柜和书架"

- Hive 只记路径，不搬数据。`ALTER LOCATION` 几毫秒完成就是证据
- 所以：**改 Hive 表的位置，数据不会跟着动**。数据在哪，是你自己负责的事
- **反过来**：数据搬到新位置而忘了改 Hive 表，Hive 就会去老地方找，报"文件不存在"

### 关系 4：Kylin 和 Hive / HBase / SpringBoot —— "三道工序"

```
Hive（原料） → Kylin（加工，结果存 HBase） → SpringBoot（取货）
```

- Kylin **读** Hive，**写** HBase
- SpringBoot **只读** Kylin，不碰 Hive、不碰 HBase
- **所以**：Hive 数据变了，Cube 不会自动更新，得重新 build；Cube 重建期间，SpringBoot 查到的还是旧数据

> 本项目里 HBase 的角色要说清楚：**它不是业务数据的存储，而是 Kylin 的"仓库"**——Cube 的实体结果、以及 Kylin 的项目/模型/Cube 定义（`kylin_metadata` 表），都存在 HBase 里。

### 分工逻辑（一句话）

**管事的在 master，干活的在 slave，看结果的在 Windows。**

- master：所有"指挥部"进程（NameNode、ResourceManager、HMaster、MySQL、Hive、Kylin）
- slave1/slave2：所有"干活"进程（DataNode 存数据、NodeManager 跑计算、HRegionServer 存 HBase 数据）
- Windows 虚拟机：不参与计算，纯粹当**一台能上内网的办公电脑**用

> 为什么 master 上没有 DataNode/NodeManager？因为 `slaves` 文件里只写了 slave1、slave2——**这是按设计来的，不是故障**。

## 六、5 个人怎么共用这一套环境 ⭐

### 6.1 先理解共用这件事的性质

**一个组只有一套环境，所有人连的是同一个 master、同一个 MySQL、同一个 Kylin。**

这意味着：

- ✅ **好处**：不用每人装一遍，装一次五个人用；数据、配置、Cube 都是共享的
- ⚠️ **代价**：**没有隔离**。A 把 HDFS 里的数据删了，B 立刻也用不了；A 执行 `stop-all.sh`，全组的接口都断

所以共用的核心不是"怎么连"，而是"**约定好谁不碰什么**"。

### 6.2 两种访问方式，对应两种活

| 方式 | 怎么进 | 适合干什么 | 谁用 |
|---|---|---|---|
| **网页终端** | 平台实验页 → 左侧任务面板 → 打开终端 | 敲命令、启动/停止服务、跑 Hive、跑 Kylin | 环境负责人（占竞、李艺淼） |

### 8.2 这次踩过的坑，按症状查

| 症状 | 根因 | 解法 |
|---|---|---|
| `File file:/tmp/... does not exist` | 缺 `fs.defaultFS` | 补进 `core-site.xml` |

## 九、答辩可以怎么说

如果老师问"你们的技术架构是什么"：

> 我们在三个节点的 Hadoop 集群上搭了一套医药数据分析平台。
>
> **存储层**：原始业务数据分两路，一路进 MySQL 5.7 存明细，供数据大屏直接查询；另一路以文本文件形式上传到 HDFS，靠三个节点的 DataNode 分布式存储、三副本冗余。
>
> **计算层**：HDS 之上用 Hive 建了 6 张外部表，把无结构的文本映射成可 SQL 查询的表；ZooKeeper 三节点集群负责协调和选主。
>
> **预计算层**：用 Kylin 做多维预计算，读取 Hive 数据构建 Cube，把十二个分析维度的聚合结果提前物化，元数据和 Cube 实体都存在 HBase 里。后端查询 Kylin 可以在毫秒级返回，避免了每次查询都扫全表。
>
> **应用层**：SpringBoot 提供 12 个 REST 接口，通过 Kylin JDBC 取数；前端用 Vue2 加 ECharts 渲染 12 张分析图；数据大屏用 Django 加 ECharts，直连 MySQL。
>
> 整套系统部署在实验平台的三个 Linux 虚拟机上，通过网页终端管理，用同网段的 Windows 虚拟机做访问入口。

### 如果被追问"遇到什么困难"

> 最典型的一个是：数据最初放在 master 的本地磁盘上，Hive 表也指向本地路径。单机查询完全正常，但一旦提交分布式作业就失败——因为计算任务被调度到 slave1、slave2 上执行，它们访问不到 master 的本地文件。
>
> 排查时发现 `core-site.xml` 里漏配了 `fs.defaultFS`，导致 Hadoop 默认使用本地文件系统。补上配置、把数据迁移进 HDFS、并修正 Hive 表的位置后，整条链路才打通。
>
> 这个问题的本质是：**单机视角和集群视角的区别**——在集群里，任何数据只有放进共享存储，才对所有计算节点可见。

## 十、名词速查

| 名词 | 一句话解释 |
|---|---|
| HDFS | 把多台机器的硬盘拼成一块，文件存多副本 |
| YARN | 计算资源的调度器，负责把任务派到哪台机器跑 |
| MapReduce | 分布式计算框架，"分开算再合并" |
| Hive | 给 HDFS 上的文件套一层 SQL 表结构，本身不存数据 |
| HBase | 建立在 HDFS 上的列式数据库，支持按行键随机读写 |
| ZooKeeper | 分布式协调服务，负责选主、登记、配置同步 |
| **Kylin** | **把多维分析结果提前算好存起来，查询时直接取答案** |
| **Cube** | **Kylin 预计算的结果集，是"答案册"本身** |
| JDBC | Java 连接数据库的标准接口 |
| DataNode | HDFS 里真正存数据的进程 |
| NodeManager | YARN 里真正跑计算任务的进程 |
| NameNode | HDFS 的"目录"，记录每个文件被切成了几块、放在哪 |
| ResourceManager | YARN 的"包工头"，负责分配计算资源 |
