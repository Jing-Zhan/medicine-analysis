## 二、集群启动

环境重启后集群不会自启，执行一键脚本：

```bash
bash /opt/start-cluster.sh
```

脚本按五个阶段顺序拉起并打印状态摘要：

1. ZooKeeper
2. HDFS + YARN
3. HBase
4. Hive metastore
5. Kylin

**启动成功的判据：**

```bash
jps                      # 应看到 QuorumPeerMain / NameNode / DataNode / ResourceManager / HMaster / HRegionServer / RunJar(metastore) / kylin 相关进程
hdfs dfs -ls /bi_data/mysql    # 6 个目录
```

Kylin 侧再看 Cube 状态，必须是 `READY`、2.95 GB、源记录 1,000,000：

```bash
# 浏览器打开 Kylin Web UI 查看，或用 curl 调 Kylin REST
```

> 踩过的坑：环境重启后 `jps` 只剩一个 jar 进程，Kylin Web 打不开、Cube 列表空白。不是数据丢了，是集群没起，跑一遍 `start-cluster.sh` 就好。Cube 会恢复成 READY，不需要重建。

## 三、MySQL 侧的准备

`yiyao` 库有 6 张表，`prescription_diseases` 100 万行，另外 5 张是维表（药品 23 万、疾病 4.2 万、医院 1777、区域 1777、科室若干）。

### 3.1 建索引（`deploy/sql/mysql_indexes.sql`）

12 个业务接口的 SQL 都要在药品码、诊断码上做多表关联。不建索引时每条 SQL 都是 100 万行全表扫描配嵌套循环，实测 7~14 秒；建完之后 2~12 秒。

关键的一条是**生成列**：

```sql
ALTER TABLE prescription_diseases
  ADD COLUMN drug_code VARCHAR(64)
  GENERATED ALWAYS AS (SUBSTRING_INDEX(m_drug, '_', 1)) STORED;
CREATE INDEX idx_drug_code ON prescription_diseases (drug_code);
```

明细表里药品码形如 `DM0000178036_2`，维表 `t_view_drug.drug` 是 `DM0000178036`，差一个 `_序号` 后缀。把去后缀这件事固化成生成列，关联才能走索引；如果直接写 `SUBSTRING_INDEX(m_drug,'_',1) = drug`，索引用不上。

其余索引：

| 表 | 索引 | 列 |
| --- | --- | --- |
| prescription_diseases | idx_drug_code / idx_diag1 / idx_section / idx_hospid | drug_code / m_diagnostic1 / m_section / hosp_id |
| t_view_drug | idx_drug | drug |
| t_view_disease | idx_dis13 | disease_type13 |
| t_view_section | idx_sec2 | section2 |
| t_view_hosp | idx_hosp | hosp_id |
| t_view_areas | idx_areas | hosp_id |

**验证：** 下面这条要返回 9 行。

```bash
mysql -uroot -p123456 yiyao -e "
SELECT TABLE_NAME, INDEX_NAME, COLUMN_NAME FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA='yiyao' AND INDEX_NAME LIKE 'idx_%' ORDER BY 1,2;" 2>/dev/null
```

### 3.2 清洗维表里的回车符（`deploy/sql/clean_crlf.sql`）

原始数据来自 Windows，维表的文本字段末尾带 `\r`，例如 `t_view_section.section_name1` 实际是 `预防保健科\r`（16 字节 / 6 字符）。不清洗的话，接口返回的 JSON 里会出现 `"中医科\r"`，前端表格显示成多余的方块。

清洗方式是先从 `information_schema` 生成 47 条 `UPDATE`，再批量执行：

```bash
mysql -N -B -uroot -p123456 2>/dev/null <<'EOF' > /tmp/clean_cr.sql
SELECT CONCAT('UPDATE `',TABLE_NAME,'` SET `',COLUMN_NAME,'`=REPLACE(REPLACE(`',COLUMN_NAME,'`,CHAR(13),""),CHAR(10),"") WHERE `',COLUMN_NAME,'`<>REPLACE(REPLACE(`',COLUMN_NAME,'`,CHAR(13),""),CHAR(10),"");')
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA='yiyao' AND TABLE_NAME LIKE 't_view_%'
  AND DATA_TYPE IN ('varchar','mediumtext','text');
EOF
mysql -uroot -p123456 --force yiyao < /tmp/clean_cr.sql
```

**验证：** 两个数字都应为 0。

```bash
mysql -uroot -p123456 yiyao -e "
SELECT COUNT(*) FROM t_view_section WHERE section_name1 <> REPLACE(REPLACE(section_name1,CHAR(13),''),CHAR(10),'');" 2>/dev/null
```

### 3.3 收窄维表列宽（`deploy/sql/shrink_varchar.sql`）

5 张维表的所有文本列原本都是 `varchar(1000)`，而实测最长只有 2~64 字符。100 万行按药品名分组时，每行都拖着 1000 字节进临时表，白搬空字节。

```bash
mysql -uroot -p123456 yiyao < deploy/sql/shrink_varchar.sql
```

脚本用一段存储过程遍历 `information_schema` 里 `CHARACTER_MAXIMUM_LENGTH > 255` 的 varchar 列，逐列取 `MAX(CHAR_LENGTH())` 后改成 `VARCHAR(GREATEST(32, 最大长度 × 2))`。**宽度由脚本自己量**，不靠人猜，避免截断。

收窄后 `t_view_drug` 数据部分 61.6 MB，全库 6 张表合计约 378 MB。这一步是纯优化，**不影响 Hive 和 Kylin 侧的数据**——那些是 HDFS 上的文本文件，与 MySQL 表结构无关，Cube 仍是 READY。改完也不需要重启后端，立即生效。

## 四、后端

### 4.1 双引擎查询网关（重要，答辩会问）

`KylinUtil` 原本只连 Kylin。现在改成一个查询网关，由 `application.properties` 里的 `query.engine` 决定连哪个库：

```properties
# kylin —— 走 Kylin 立方体
# mysql  —— 走 MySQL 明细库（当前部署值）
query.engine=mysql
```

选 `mysql` 的原因见第七节。切到 `mysql` 时，网关会把 Kylin 方言的 SQL 自动改写成 MySQL 方言，**24 处 SQL 语句、12 个 Service 方法一行都不用改**。

改写规则：

| Kylin 侧 | MySQL 侧 | 原因 |
| --- | --- | --- |
| `BIGDATA.PRESCRIPTION_DISEASES` | `prescription_diseases` | 表名 |
| `BIGDATA.SECTION` / `DISEASE` / `DRUG` / `HOSPITAL` / `HOSP_AREA` | `t_view_section` / `t_view_disease` / `t_view_drug` / `t_view_hosp` / `t_view_areas` | 表名，且 MySQL 在 Linux 上表名区分大小写 |
| `PRESCRIPTION_DISEASES.M_DIAGNOSTIC` | `m_diagnostic1` | 两侧列名不同 |
| `PRESCRIPTION_DISEASES.AGE` | `m_age` | 两侧列名不同 |
| `PRESCRIPTION_DISEASES.M_DRUG = DRUG.DRUG` | `PRESCRIPTION_DISEASES.DRUG_CODE = DRUG.DRUG` | 走生成列索引 |
| `CAST(x AS VARCHAR)` | `CAST(x AS CHAR)` | MySQL 的 CAST 不接受不带长度的 VARCHAR |
| `'201' + SUBSTRING(...)` | `CONCAT('201', SUBSTRING(...))` | MySQL 里 `+` 是数值加法，`'201'+'1'` 会算成 202 |

> 注意：MySQL 的**列名不区分大小写**，所以 `M_SECTION`、`M_SEX`、`AMOUNT` 这类不需要改写；只有表名在 Linux 上区分大小写，以及上面几个真正改了名字的列才需要映射。

## 五、前端

### 5.1 为什么打进后端 jar（不是独立部署）

前端请求走 `vue-http-rexsheng`，其 `dataType` 默认是 `"json"`，也就是 **XHR 而不是 JSONP**。如果前端跑在 8080、后端跑在 83，就构成跨域，而 Spring Boot 默认不放行，所有请求会失败。

原先的方案是「`dist` 丢 Tomcat、`baseUrl` 指向另一个 IP」，在这个环境里必然全挂。改成**同源部署**：

- `dist` 的全部内容放进 `backend/yiyao/src/main/resources/static/`
- `src/config.js` 里 `baseUrl: ''`（相对路径）
- 打包进 jar，由 83 端口一起提供

好处：没有跨域配置、不用另起静态服务器、换 `localhost` 或任何 IP 访问都自动正确。

### 5.2 怎么重新打包前端（Node 24 也能打）

工程是 Vue 2 + webpack 3，文档要求 Node 14.16.1。但 webpack 3 在 Node 17+ 上失败的真正原因是 OpenSSL 3 移除了 md4 摘要，加一个参数即可绕过，**不需要装旧版 Node**：

```bash
cd frontend/bigdataInCase-Medicine
npm install --ignore-scripts --no-audit --no-fund     # 约 1 分钟，1669 个包
NODE_OPTIONS=--openssl-legacy-provider npm run build  # 约 6 秒
```

实测在 Node 24.14.0 / npm 11.9.0 上打包成功，webpack 3.12.0。stderr 里那一串 `Accessing non-existent property 'mkdir' of module exports` 是 shelljs 的循环依赖警告，无害。

打完把 `dist/*` 复制到 `backend/yiyao/src/main/resources/static/`，再跑一遍 `mvn package`。

`assetsPublicPath` 是 `./`（相对路径），所以产物放在任何路径下都能直接跑。

### 5.3 假数据开关

`src/config.js`：

```js
baseUrl: '',        // 部署版：同源
useMock: false,     // 部署版必须 false，否则图表永远显示假数据
```

`src/api/index.js` 里还有一个兜底：真实请求失败或超时时用假数据渲染，避免演示时页面空白。**阈值是 `FALLBACK_TIMEOUT = 60000`（60 秒）**。

> 这个值最初是 8 秒，是个 bug：12 个接口实测 2~12.5 秒，8 秒一到就把「还在算」误判成「接口挂了」，直接把真实数据换成假数据，首页一度出现「概览卡片是真的、下面三张图是假的」这种混杂状态。另外后端明确返回错误时也不再拿假数据顶替，避免界面看起来正常、实际展示编造数字。

## 七、为什么高基数关联走 MySQL 而不是 Kylin

这是本项目最重要的一个工程判断，答辩必问。

**已完成的部分：** Kylin 部署、数据源配置、模型 `bi_model`、Cube `bi_cube` 全部按要求做完，Cube 状态 `READY`、2.95 GB、源记录 100 万，Kylin 自身的 Insight 查询验证通过。

**问题：** 12 个业务接口的 SQL 全都是「事实表 LEFT JOIN 5 张维表」。而 `bi_cube` 是单表模型（只含事实表 8 个维度、2 个度量），Kylin 无法用这张 Cube 回答带维表关联的 SQL，12 个接口一律返回空集。

**把维表全部加进模型的代价（实测外推）：**

- 现状：8 个维度 → 2⁸ = 256 个 cuboid → 构建 25 分钟 → 占 2.95 GB
- 12 个接口实际用到 20 个不同列，跨 6 张表 → 2²² ≈ 419 万个 cuboid
- 按 2⁸ 的实测数据线性外推 → 约 291 天

这是组合爆炸，不是机器慢的问题，加内存加 CPU 也解决不了。

**采用的方案：** 低基数、单表的聚合走 Kylin；需要在药品（23 万基数）、诊断（4.2 万基数）上做明细关联的走 MySQL，并在 MySQL 侧用生成列加索引把关联成本压下来。接口层用 `query.engine` 配置项切换，SQL 由网关自动改写方言，业务代码无感知。

**这也解释了课程资料里「全维度约 10 分钟构建」为什么做不到：** 那是在小数据量下的说法。100 万行、22 个维度列的实际情况是组合爆炸，必须做取舍。

## 八、故障记录

部署过程中踩到的问题，按出现顺序：

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 服务器连不上 GitHub，`curl` 卡死或 `Empty reply` | DNS 被污染，解析到错误 IP（`57.155.223.240`），TLS 握手超时 | 仓库设为 public，改用镜像下载 tarball：`curl -L "https://ghproxy.net/https://github.com/<user>/<repo>/archive/refs/heads/main.tar.gz"` |
| `python3: command not found` | 镜像未预装 | `yum install -y python3`（装到 3.6.8） |
| Django 4.2 装不上 | 需要 Python ≥ 3.8，而系统只有 3.6.8 | 降到 `Django==3.2.25`；配套 `PyMySQL==1.0.2`（1.1 需要 ≥ 3.7） |
| Django 启动报 `SQLite 3.9.0 or later is required` | 系统 SQLite 是 3.7.17 | 该项目用 PyMySQL 直连，不依赖 Django ORM，把 `DATABASES` 的 `ENGINE` 改成 `django.db.backends.dummy` |
| 12 个接口全部返回 `{"code":200,"data":[]}` | Cube 单表模型，无法回答带维表关联的 SQL | 改用 MySQL 路线（见第七节） |
| `/home/citylevel` 报 `Expression #1 of SELECT list is not in GROUP BY clause` | `SELECT` 里是 `CONCAT(...)`，而 `GROUP BY` 里是内层 `SUBSTRING(...)`；MySQL 的 `ONLY_FULL_GROUP_BY` 要求两边表达式完全一致，不会推导「外层套了 CONCAT 仍等价」 | `GROUP BY`、`ORDER BY` 同步改成 `CONCAT(...)` |
| 查 `year_month` 报 `ERROR 1064` 语法错误 | `YEAR_MONTH` 是 MySQL 保留字（`INTERVAL ... YEAR_MONTH` 用掉了） | 加反引号；带表名限定的写法（`别名.YEAR_MONTH`）合法，不需要改写 |
| 查 `year_month` 时「无输出、也不报错」 | 命令加了 `2>/dev/null`，把 stderr 和真实错误一起丢了 | 排查阶段不要把 stderr 重定向掉 |
| 建索引时终端长时间无输出，误以为卡死而被 Ctrl+C 中断 | 100 万行建索引期间不打印任何进度 | 放到后台执行（`nohup ... &`），用 `information_schema.PROCESSLIST` 查进度 |
| 首页「概览是真的、图表是假的」 | 前端 8 秒兜底把慢查询误判为失败 | `FALLBACK_TIMEOUT` 改为 60 秒；后端返回错误时不再用假数据顶替 |

## 九、当前性能实测

优化前后对比（`curl -w '%{time_total}'`，热缓存）：

| 接口 | 优化前 | 优化后 |
| --- | --- | --- |
| `/home/overview` | 0.61 | 0.81 |
| `/home/citylevel` | 7.49 | **2.17** |
| `/home/age` | 7.48 | **2.17** |
| `/home/province` | 7.33 | **1.92** |
| `/drug/cities` | 8.30 | 5.46 |
| `/drug/hospital` | 12.58 | 11.09 |
| `/home/top10` | 12.61 | 9.51 |
| `/disease/union` | 13.77 | 12.50 |
| `/disease/drug` | 13.48 | 12.53 |
| `/disease/age` | 8.40 | 7.19 |
| `/disease/section` | 8.83 | 8.96 |
| `/drug/diseases` | 13.57 | 12.45 |
| `/drug/section` | 13.84 | 12.16 |

**规律：** 不需要 join `t_view_drug` 的查询降到 2 秒左右（3.5~3.8 倍提升）；需要 join 并按药品名分组的仍要 9~12 秒，瓶颈是 100 万次 varchar 长键的 B 树探测本身，不是行宽也不是缺索引。

**判断：** 首屏 5 张图并行加载，最慢的一张约 12 秒出图。配合前端 60 秒兜底，不会误判、不会串假数据。进一步提速需要预聚合中间表（相当于自建小 Cube），超出本次实训时间范围，作为已知优化方向记录。
